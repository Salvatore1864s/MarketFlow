# Architecture Decision Records (ADR)

В этом документе записаны основные решения, которые были приняты при разработке MarketFlow.

## ADR-001: Использование микросервисной архитектуры

**Статус:** Принято

**Контекст:**

По заданию нужно создать систему из нескольких сервисов, которые взаимодействуют друг с другом.

**Решение:**

Использовать пять микросервисов:
- Identity
- Catalog
- Orders
- Inventory
- Payment

**Причина:**

Каждый сервис отвечает за свою часть проекта. Так проще разделять задачи и работать над разными частями системы независимо.

## ADR-002: PostgreSQL для хранения данных

**Статус:** Принято

**Контекст:**

Каждому сервису нужно хранить свои данные.

**Решение:**

Использовать PostgreSQL. Для каждого микросервиса создана отдельная база данных.

**Причина:**

PostgreSQL подходит для хранения данных и работы с транзакциями. Отдельные базы помогают разделить данные разных сервисов.

## ADR-003: RabbitMQ для обмена сообщениями

**Статус:** Принято

**Контекст:**

Сервисам нужно передавать друг другу информацию, например о резервировании товара и результате оплаты.

**Решение:**

Использовать RabbitMQ для обмена сообщениями между микросервисами.

**Причина:**

Сервисы могут отправлять и получать сообщения независимо друг от друга. Им не нужно постоянно обращаться друг к другу напрямую.

## ADR-004: Saga для оформления заказа

**Статус:** Принято

**Контекст:**

Оформление заказа состоит из нескольких действий: резервирование товара, оплата и подтверждение заказа.

Если одно из действий завершается ошибкой, нужно отменить предыдущие действия.

**Решение:**

Использовать Saga для управления процессом оформления заказа.

**Причина:**

Saga позволяет выполнять действия по очереди и отменять предыдущие действия, если заказ не удалось оформить.

## ADR-005: Outbox для отправки сообщений

**Статус:** Принято

**Контекст:**

При создании заказа нужно сохранить изменения в базе данных и отправить сообщение в RabbitMQ. Если приложение завершится с ошибкой между этими действиями, сообщение может потеряться.

**Решение:**

Использовать Outbox Pattern. Сообщение сначала сохраняется в базе данных, а затем отдельный процесс отправляет его в RabbitMQ.

**Причина:**

Это снижает вероятность потери сообщений и помогает сохранить согласованность данных.

## ADR-006: Redis для временного хранения данных

**Статус:** Принято

**Контекст:**

Некоторые данные не обязательно каждый раз получать из основной базы данных.

**Решение:**

Использовать Redis для кэширования и временного хранения данных.

**Причина:**

Это позволяет быстрее получать данные и уменьшает количество повторных обращений к базе данных.

## ADR-007: SignalR для уведомлений

**Статус:** Принято

**Контекст:**

Покупателю нужно сообщать об изменении статуса заказа без постоянного обновления страницы.

**Решение:**

Использовать SignalR для отправки уведомлений в реальном времени.

**Причина:**

Покупатель может получать уведомления об изменении статуса заказа сразу после обработки заказа.

## ADR-008: YARP для API Gateway

**Статус:** Принято

**Контекст:**

В проекте несколько микросервисов, и клиенту неудобно обращаться к каждому из них отдельно.
