# Архитектура MarketFlow

## 1. О проекте

MarketFlow — это маркетплейс, в котором покупатели могут смотреть товары, добавлять их в корзину и оформлять заказы. Продавцы могут добавлять и редактировать свои товары.

Основные возможности:
- Регистрация и вход в аккаунт.
- Просмотр и поиск товаров.
- Управление товарами продавца.
- Корзина и оформление заказов.
- Проверка наличия товаров.
- Резервирование товаров на складе.
- Имитация оплаты.
- Просмотр статуса заказа.
- Получение уведомлений об изменении статуса заказа.

## 2. Как устроен проект

Проект разделён на несколько частей:
- Клиентская часть на React.
- API Gateway, через который проходят запросы.
- Пять отдельных микросервисов.
- Базы данных PostgreSQL.
- Сервисы для обмена сообщениями и хранения временных данных.

Каждый микросервис отвечает за свою часть проекта. Благодаря этому разные части системы можно разрабатывать и запускать отдельно.

## 3. Микросервисы

### Identity Service

Отвечает за пользователей и вход в систему.

Основные функции:
- Регистрация.
- Авторизация.
- Выдача JWT-токенов.
- Работа с ролями пользователей.

Использует PostgreSQL.

### Catalog Service

Отвечает за товары.

Основные функции:
- Добавление товаров.
- Редактирование товаров.
- Удаление товаров.
- Просмотр и поиск товаров.
- Фильтрация товаров.

Использует PostgreSQL.

### Orders Service

Отвечает за корзину и заказы.

Основные функции:
- Работа с корзиной.
- Создание заказов.
- Просмотр истории заказов.
- Изменение статусов заказов.
- Управление процессом оформления заказа.
- Отправка сообщений другим сервисам.

Для сохранения заказов и сообщений используется PostgreSQL.

### Inventory Service

Отвечает за количество товаров на складе.

Основные функции:
- Хранение информации об остатках.
- Резервирование товаров при оформлении заказа.
- Подтверждение резерва.
- Освобождение резерва, если заказ не удалось оформить.

Использует PostgreSQL.

### Payment Service

Отвечает за обработку оплаты.

В проекте используется имитация оплаты, без настоящих банковских операций.

Основные функции:
- Получение запроса на оплату.
- Обработка оплаты.
- Отправка результата в Orders Service.

Использует PostgreSQL.

## 4. Используемые технологии

- **C# и ASP.NET Core** — разработка серверной части.
- **React** — клиентская часть.
- **PostgreSQL** — хранение данных каждого микросервиса.
- **YARP** — API Gateway, через который проходят запросы.
- **RabbitMQ** — обмен сообщениями между сервисами.
- **Redis** — хранение временных данных и кэширование.
- **SignalR** — отправка уведомлений в реальном времени.
- **Docker Compose** — запуск необходимых сервисов и баз данных.
- **xUnit** — написание автоматических тестов.
- **GitHub Actions** — автоматическая проверка проекта.

## 5. Как сервисы взаимодействуют друг с другом

Клиент отправляет запросы через API Gateway. Gateway направляет запрос в нужный микросервис.

Для обычных запросов используется HTTP. Когда сервисам нужно передать событие или результат своей работы, используется RabbitMQ.

У каждого микросервиса своя база данных. Один сервис не обращается напрямую к базе другого сервиса.

## 6. Как проходит оформление заказа

Для оформления заказа используется следующий порядок:

1. Покупатель создаёт заказ.
2. Orders Service сохраняет заказ со статусом ожидания.
3. В базе данных сохраняется сообщение, которое нужно отправить в RabbitMQ.
4. Inventory Service получает сообщение и проверяет наличие товара.
5. Если товар есть, он резервируется.
6. Orders Service отправляет запрос на оплату.
7. Payment Service обрабатывает оплату и отправляет результат.
8. Если оплата прошла успешно, резерв товара подтверждается, а заказ получает статус Confirmed.
9. Если оплата не прошла, резерв освобождается, а заказ получает статус Cancelled.
10. Покупатель получает уведомление об изменении статуса заказа через SignalR.

Если на одном из этапов возникает ошибка, система старается отменить предыдущие действия. Например, если оплата не прошла, товар возвращается в доступный остаток.

## 7. Сохранение и отправка сообщений

Для отправки сообщений используется Outbox Pattern.

Смысл простой: сначала сообщение сохраняется в базе данных вместе с изменениями заказа, а затем отдельный процесс отправляет его в RabbitMQ.

Это помогает не потерять сообщение, если во время оформления заказа возникнет ошибка.

Также в сервисах добавлена проверка повторных команд. Она нужна, чтобы повторное получение одного сообщения не приводило к повторному резервированию или списанию товара.

## 8. Безопасность

В проекте используются:
- JWT для авторизации.
- Роли пользователей для ограничения доступа.
- Проверка прав на сервере.
- Хранение паролей в виде хэшей.
- Переменные окружения для настроек и секретных данных.

## 9. Тестирование

Для тестирования используется xUnit.

В проекте есть тесты для Catalog, Orders, Inventory и Payment.

Проверяются основные действия сервисов, работа с заказами, резервирование товаров и повторное получение команд.

Также есть интеграционные тесты SignalR: проверяется подключение покупателя, запрет подключения продавца и получение уведомлений только своей группой.

На момент последней проверки все 49 тестов прошли успешно.

## 10. Запуск проекта

Для запуска инфраструктуры используется Docker Compose.

В проекте используются отдельные базы PostgreSQL для микросервисов, а также RabbitMQ и Redis.

Настройки подключения и другие секретные значения задаются через переменные окружения.

## 11. Итог

MarketFlow построен на основе микросервисной архитектуры. Каждый сервис отвечает за отдельную часть работы маркетплейса.

Для обмена сообщениями используется RabbitMQ, для оформления заказа — последовательность действий с возможностью отмены предыдущих шагов, а для уведомлений — SignalR.

Такой подход помогает разделить проект на понятные части и упростить дальнейшую разработку.
